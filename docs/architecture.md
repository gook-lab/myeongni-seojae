# 구조와 게이트

> 어떻게 짜여 있고, 무엇이 배포를 막는가.

[← 명리서재](../README.md)

## 설계 결정

| 결정 | 이유 |
|---|---|
| **시간 미상이 기본 입력** | 관객이 부모님 세대입니다. 태어난 시각을 모르는 것이 정상이지 예외가 아닙니다. 그리고 **대운 타임라인은 시주를 참조하지 않아** 시각 없이도 100% 정확합니다 |
| **점수를 전부 없앰** | 기존 구현은 `Math.sin`으로 운세 점수를 만들고 있었습니다. 명리에 정설화된 점수법이 없으므로 새 산식을 만드는 것도 근거 없는 숫자를 포장하는 거입니다. 텍스트만 남겼습니다 |
| **URL에 생년월일 없음** | Sentry가 `location.href`를 이벤트에 담습니다. 다시보기는 localStorage만 씁니다 |
| **React Query 미사용** | 서버 상태가 0개입니다. 쿼리할 서버가 없는데 서버 상태 캐시를 둘 이유가 없습니다 |
| **계산 라이브러리 지연 로드** | 입력 화면을 보는 데 계산 코드가 필요 없습니다. 구형 안드로이드 + 느린 회선이 관객이기 때문입니다 |

## 구조

```
src/
  core/           순수 함수. React·Zustand·Sentry 를 import 하지 않는다
    korea-time.ts   핵심 — 두 타임라인 + tzdata 런타임 자가진단
    manse.ts        사주 원국. 라이브러리를 두 번 호출한다 (아래 참조)
    daeun.ts        대운 타임라인. 시주를 참조하지 않는 것이 계약이다
    input.ts        검증 + 음양력. 예외를 던지지 않고 SajuResult 를 반환
    errors.ts       SajuError 유형
    regions.ts      출생지 경도
  text/           데이터만. 계산 로직 없음
    interpret.ts    카테고리별 단일 테이블
    daeun-text.ts   십성 10종 대운 문단
  engine/         동적 import 대상. lunar-javascript 와 텍스트를 여기서 끌고 온다
  ui/             상태와 부수효과를 아는 유일한 계층
  observability/  Sentry PII 차단
```

### 이중 라이브러리 호출 — 교차 검증

`lunar-javascript`의 절기표는 **UTC+8 기준**으로 계산돼 있습니다
(검증: 1957 입춘 = `1957-02-04 09:54:37` CST).

- **년주·월주**는 "출생 순간이 절기 순간보다 앞이냐 뒤냐"로 정해집니다. 두 순간의
  비교이므로 같은 타임라인에 올려놓기만 하면 되고, 경도 보정분은 양변에서 상쇄됩니다.
  → 출생시각을 UTC+8로 읽어서 줘요 (`cstFields`)
- **시주·일주**는 "해가 하늘 어디에 있었나"이므로 진태양시여야 합니다.
  → `solarFields`

두 필드는 27분 55초 차이가 납니다. 절기 경계 ±28분에 태어난 사람에게 실제로 다른
결과를 줘요. 그래서 한 번 호출로 뭉개지 않습니다.

## 배포 게이트

**사람이 눈으로 못 잡는 종류의 실패**만 여기서 막습니다. 눈으로 보이는 것은
어차피 보이니까 게이트에 넣을 이유가 없습니다.

CI는 러너의 tzdata가 한국 표준시 이력을 아는지부터 확인합니다. ICU가
빈약하면 나머지가 통째로 거짓 통과합니다.

| 단계 | 무엇을 막나 |
|---|---|
| tzdata 자가진단 | 러너의 시간대 자료가 결손이면 1954~61 구간이 조용히 틀립니다 |
| 타입체크 | — |
| 빌드 · MCP 빌드 | 번들 게이트가 볼 `dist`를 만들습니다 |
| 단위 테스트 | 아래 다섯 게이트가 여기 들어 있습니다 |
| MCP stdio 실기동 | 단위 테스트는 `handleTool`만 불러요. 전송 계층이 죽어도 모릅니다 |
| E2E (모바일 · 데스크톱 · 움직임) | 사람이 끝까지 갈 수 있는지 확인합니다 |
| 문서 숫자 대조 | 손으로 적은 숫자는 반드시 낡습니다 |
| 골든 재생성 diff | 정답지가 코드와 어긋나 있으면 실패합니다 |

### 단위 테스트 안의 다섯 게이트

**1. 골든** — 만세력이 조용히 틀리는 것을 막습니다. 54건의 명식을 스냅샷으로
고정하고 독립 구현(`manseryeok` v2)과 교차 대조합니다. 갈리는 자리는 전부
이유가 분류돼 있어야 하며 `unexplained`가 하나라도 나오면 실패합니다.

```
true-solar-time        16건  경도 보정 유무 (규약 차이)
yajasi                  5건  23시대 시두 유파 (규약 차이)
standard-time-history   2건  manseryeok 이 틀리는 자리
```

**2. 절기·일주 천체력 대조** — 표를 다른 표와 맞추는 것으로는 둘 다 틀린
경우를 못 걸러냅니다. 천체력과 율리우스일로 방법을 바꿔 대조합니다.

**3. 프라이버시** — 생년월일이 Sentry로 새는 것을 막습니다.
`location.href` / Session Replay / breadcrumbs / error context 네 경로를
전부 막고, 막혔는지를 테스트가 확인합니다. 설정은 언제든 실수로 풀릴 수 있습니다.

**4. 번들** — 진입 청크 250KB 예산, 엔진 청크 150KB, 계산 라이브러리가
번들에 없을 것, 그리고 **바깥 호스트를 부르지 않을 것**. CDN 한 줄이면
조용히 되돌아가는 종류입니다.

**5. 색 대비** — `styles.css`를 직접 읽어 WCAG AA를 계산합니다. 흐린 글씨는
"차분한 톤"이 아니라 안 보이는 글씨기 때문입니다.

## 수동 운영 항목

게이트에 넣지 않은 것들입니다. 외부 자원이 필요하거나 사람이 판단해야 하기 때문입니다.

```bash
pnpm verify:python 150  # 파이썬 독립 구현과 대조 (천체력 17MB · 파이썬 환경)
pnpm verify:kasi        # 한국천문연구원 공식 절기 (공공데이터 키 필요)
pnpm gen:terms          # 절기표 다시 생성 (astronomy-engine)
pnpm fonts              # 웹폰트 다시 받기
pnpm shots              # 문서용 스크린샷 갱신
pnpm docs:sync          # README 의 테스트 수를 실제와 맞춤
```

## 개발

```bash
pnpm install
pnpm dev              # 개발 서버
pnpm test             # 단위 테스트
pnpm test:e2e         # E2E (모바일 + 데스크톱)
pnpm test:all         # 타입체크 + 빌드 + 전체 테스트
pnpm golden:gen       # 골든 정답지 재생성
```

**골든 정답지를 갱신할 때는 diff를 반드시 눈으로 확인해야 합니다.** 테스트가 통과한다는
것은 "예전과 같다"는 뜻이지 "맞다"는 뜻이 아니기 때문입니다.
