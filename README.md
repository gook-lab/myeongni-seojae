# 명리서재

인생을 10년 단위로 펼쳐보는 사주 사이트.

대부분의 사주 앱은 "오늘의 운세 87점"에 집중한다. 그런데 사람들이 진짜 소름 돋는
순간은 오늘 점수가 아니라 **자기 과거가 설명될 때**다. 인생을 10년 단위로 펼쳐놓고
"여기가 당신의 25~34세, 편관 대운"이라고 짚어주면 사람들은 자기 인생을 그 표에
대조한다. 맞으면 캡처해서 친구한테 보낸다.

그리고 이건 **알고리즘이 정확해야만 성립하는 유일한 기능**이다. 오늘 운세는 하루
틀려도 아무도 모르지만, 대운수가 1년 어긋나면 타임라인이 통째로 밀린다.

---

## 이 프로젝트가 실제로 고친 것

만세력이 어렵다고 하면 사람들은 절기 천문 계산을 떠올린다. **틀렸다.** 절기 계산은
이미 라이브러리가 풀어놨다. 앱마다 사주 결과가 갈리는 진짜 이유는 **한국 표준시
변경 이력**이다. 천문학이 아니라 행정 데이터다.

한국은 표준자오선이 네 번 바뀌었고 서머타임도 세 시기 있었다. 그래서 시계 시각을
진태양시로 바꾸는 보정량은 **상수가 아니다.**

| 시계 기준 | 보정량 | 해당 구간 |
|---|---|---|
| UTC+9:00 | −32분 05초 | 1912~54, 1961~현재 |
| UTC+8:30 | **−2분 05초** | 1954~61 겨울 |
| UTC+9:30 | −62분 05초 | 1954~61 서머타임 |
| UTC+10:00 | −92분 05초 | 1987~88 서머타임 |

흔한 오구현은 "서울 126.978°E, 표준자오선 135°E → −32분"을 상수로 박는 것이다.
그러면 1954~61년생 시주가 30분 어긋난다. 시주는 2시간 단위라 경계 ±30분 출생자가
통째로 오답이 된다. 부모님 세대가 정확히 그 구간이다.

### 실제로 갈리는 예

npm에 배포된 만세력 라이브러리 `manseryeok`과 대조한 결과다.

```
1957-02-04, 실제 한국 표준시 UTC+8:30
  입춘(UTC 01:55)을 당시 시계로 읽으면 KST 10:25:00
  출생 KST 10:30 → 입춘 이후

  명리서재     丁酉 壬寅   ✓
  manseryeok  丙申 辛丑   ✗  (KST=UTC+9 로 고정 가정)
```

년주와 월주가 **둘 다** 다르다. 같은 사람인데 완전히 다른 사주가 나온다.

### 해법 — 시대 분기를 없앤다

```
1) 시계시각 + 'Asia/Seoul'  →  UTC        [IANA tzdata 가 전담]
2) UTC + 경도/15h           →  진태양시    [시대와 무관한 상수 하나]
```

두 지점 사이에 시대별 표를 손으로 들고 있을 이유가 없다. tzdata가 이미 갖고 있고,
위 네 보정량은 이 공식에서 자동으로 도출된다. 손으로 쓴 표는 서머타임 시행 날짜를
틀리지만 tzdata는 안 틀린다.

검증 (Node v24, `Intl` + `Asia/Seoul`):

| 날짜 | 실측 | 구간 |
|---|---|---|
| 1910-06-15 | GMT+08:30 | 대한제국기 |
| 1930-06-15 | GMT+09:00 | 일제강점기 |
| 1957-06-15 | GMT+09:30 | UTC+8:30 + 서머타임 |
| 1957-12-15 | GMT+08:30 | UTC+8:30 겨울 |
| 1987-07-15 | GMT+10:00 | 1987 서머타임 |
| 1990-08-15 | GMT+09:00 | 현재 |

## 설계 결정

| 결정 | 이유 |
|---|---|
| **시간 미상이 기본 입력** | 관객이 부모님 세대다. 태어난 시각을 모르는 게 정상이지 예외가 아니다. 그리고 **대운 타임라인은 시주를 참조하지 않아** 시각 없이도 100% 정확하다 |
| **점수를 전부 없앰** | 기존 구현은 `Math.sin`으로 운세 점수를 만들고 있었다. 명리에 정설화된 점수법이 없으므로 새 산식을 만드는 것도 근거 없는 숫자를 포장하는 것이다. 텍스트만 남겼다 |
| **URL에 생년월일 없음** | Sentry가 `location.href`를 이벤트에 담는다. 다시보기는 localStorage만 쓴다 |
| **React Query 미사용** | 서버 상태가 0개다. 쿼리할 서버가 없는데 서버 상태 캐시를 둘 이유가 없다 |
| **계산 라이브러리 지연 로드** | 입력 화면을 보는 데 계산 코드가 필요 없다. 구형 안드로이드 + 느린 회선이 관객이다 |

## 배포 게이트

두 가지가 통과해야만 배포한다. 둘 다 **사람이 눈으로 못 잡는 종류의 실패**다.

**1. 골든 테스트** — 만세력이 조용히 틀리는 것을 막는다.
50건의 명식을 스냅샷으로 고정하고, 독립 구현(`manseryeok` v2)과 교차 대조한다.
갈리는 자리는 전부 이유가 분류돼 있어야 하며 `unexplained`가 하나라도 나오면 실패다.

```
true-solar-time        16건  경도 보정 유무 (규약 차이)
yajasi                  5건  23시대 시두 유파 (규약 차이)
standard-time-history   2건  manseryeok 이 틀리는 자리
```

**2. 프라이버시 게이트** — 생년월일이 Sentry로 새는 것을 막는다.
`location.href` / Session Replay / breadcrumbs / error context 네 경로를 전부 막고,
막혔는지를 테스트가 확인한다. 설정은 언제든 실수로 풀릴 수 있어서 테스트가 본체다.

CI는 러너의 tzdata가 한국 표준시 이력을 아는지부터 확인한다. ICU가 빈약하면 골든이
통째로 거짓 통과할 수 있기 때문이다.

## 구조

```
src/
  core/           순수 함수. React·Zustand·Sentry 를 import 하지 않는다
    korea-time.ts   ★심장★ 두 타임라인 + tzdata 런타임 자가진단
    manse.ts        사주 원국. 라이브러리를 두 번 호출한다 (아래 참조)
    daeun.ts        대운 타임라인. 시주를 참조하지 않는 것이 계약이다
    input.ts        검증 + 음양력. 예외를 던지지 않고 SajuResult 를 반환
    errors.ts       SajuError 유형
    regions.ts      출생지 경도
  text/           데이터만. 계산 로직 없음
    interpret.ts    카테고리별 단일 테이블
    daeun-text.ts   십성 10종 대운 문단
  engine/         동적 import 대상. lunar-javascript 와 텍스트를 여기서 끌고 온다
  ui/             상태와 부수효과를 아는 유일한 계층
  observability/  Sentry PII 차단
```

### 왜 라이브러리를 두 번 호출하는가

`lunar-javascript`의 절기표는 **UTC+8 기준**으로 계산돼 있다
(검증: 1957 입춘 = `1957-02-04 09:54:37` CST).

- **년주·월주**는 "출생 순간이 절기 순간보다 앞이냐 뒤냐"로 정해진다. 두 순간의
  비교이므로 같은 타임라인에 올려놓기만 하면 되고, 경도 보정분은 양변에서 상쇄된다.
  → 출생시각을 UTC+8로 읽어서 준다 (`cstFields`)
- **시주·일주**는 "해가 하늘 어디에 있었나"이므로 진태양시여야 한다.
  → `solarFields`

두 필드는 27분 55초 차이가 난다. 절기 경계 ±28분에 태어난 사람에게 실제로 다른
결과를 준다. 그래서 한 번 호출로 뭉개지 않는다.

## 개발

```bash
pnpm install
pnpm dev              # 개발 서버
pnpm test             # 단위 테스트
pnpm test:e2e         # E2E (모바일 + 데스크톱)
pnpm test:all         # 타입체크 + 빌드 + 전체 테스트
pnpm golden:gen       # 골든 정답지 재생성
```

**골든 정답지를 갱신할 때는 diff를 반드시 눈으로 확인할 것.** 테스트가 통과한다는
것은 "예전과 같다"는 뜻이지 "맞다"는 뜻이 아니다.

### 참고 자료

그대로 옮겨왔다 — 계산은 버렸지만 글은 자산이다.

## 화면 구조 — 쌓지 않고 가른다

```
홈  [사주 보기]  [오늘] [궁합] [신년]
      ↓            ↓      ↓      ↓
    입력                별도 화면
      ↓
    인생 타임라인 · 사주팔자        (2.9 화면)
      ├─ [상세 풀이 보기]  용신 · 궁위 · 오행 균형 · 풀이
      └─ [리포트 · 인쇄]   A4 문서 (브라우저 인쇄 → PDF)
```

원안 와이어플로우 그대로다. 한 번 부가 기능을 결과 페이지 하단에 탭으로
쌓아봤는데, 결과 화면이 3.8화면 길이에 버튼 18개가 되면서 대운 타임라인이
주인공 자리를 잃었다.

**문제는 기능 개수가 아니라 쌓아놓은 것이었다.** 홈에서 갈라놓으니
기능을 하나도 잃지 않으면서 타임라인 화면이 깨끗해졌다. 결과 화면의
섹션은 셋뿐이다 — 인생 타임라인(주인공), 사주팔자(근거), 풀이(원국 해석).

부가 화면은 원국이 있어야 열린다. 사주를 먼저 보지 않으면 잠겨 있고,
눌러도 입력 화면으로 보낸다.

상세 풀이도 별도 화면이다. 궁위·오행 균형·풀이를 결과 화면에 쌓았더니
5.2화면이 됐고, 원안대로 갈라놓으니 2.9 + 2.6 으로 나뉘었다.

## 리포트 — 계산 근거를 같이 싣는다

관객이 부모님 세대다. 그 세대는 스크롤을 안 하고 종이를 본다.
브라우저 인쇄로 A4 문서가 나오고 "PDF로 저장" 하면 파일이 된다.
외부 라이브러리 없이 print CSS 만 쓴다.

다른 사주 리포트와 다른 점은 **결론만 적지 않는다**는 것이다.

```
계산 근거
  출생 당시 한국 표준시 UTC+9:30 (서머타임 적용 중)
  진태양시 보정 −62분 05초 — 출생지 126.978°E 기준
  야자시 일주 유지 · 균시차 미적용
  태어난 시각 없이 계산했습니다. 대운 타임라인은 시각과 무관하므로
  그대로 정확하고, 시주와 오행 분포만 여섯 자 기준입니다.
```

"당신은 신강입니다" 만 적힌 문서는 다시 읽을 이유가 없다. 근거가 적힌
문서는 나중에 다른 곳과 대조해볼 수 있다. 용신 자리별 계산도 화면에서는
접어두지만 문서에는 펼쳐서 넣는다.

## 신살 — 겁주지 않는다

신살은 이름에 살(殺)이 붙어 오래 겁주는 데 쓰여 왔다. 도화살은 바람기,
역마살은 떠돌이 팔자, 백호대살은 피를 본다 하는 식이다.

실제로는 기운의 결이다. 도화는 사람을 끌어당기는 힘이고 역마는 움직이는
힘이다. 지금 세상에서 도화는 매력이고 역마는 글로벌 커리어다.

그래서 문장 규칙을 셋 두고 **테스트가 지킨다**.

1. 그 기운이 무엇인지 먼저 말한다
2. 잘 쓰일 때와 걸림돌이 될 때를 같이 적는다
3. "조심하세요" 로 끝내지 않는다

테스트는 긍정 단어 화이트리스트가 아니라 **재해석 표지**를 본다 —
"오히려", "실제로는", "~가 아니라" 처럼 통념을 뒤집는 말이 살(殺) 이름이
붙은 항목마다 반드시 하나는 있어야 한다. 옛 공포 표현("피를 본다")은
인용해서 부정할 때만 허용한다.

판정에는 근거를 붙인다. "도화살이 있습니다" 로는 확인할 방법이 없지만
`도화 · 년지 酉 기준 → 월지 午` 는 다른 곳과 대조할 수 있다.

넣은 것 13종: 도화 · 역마 · 화개 · 천을귀인 · 문창귀인 · 금여 · 양인 ·
홍염 · 원진 · 귀문관 · 백호대살 · 괴강 · 천라지망.

삼재·대장군처럼 해마다 바뀌는 것은 넣지 않았다. 원국의 성질이 아니고
공포 마케팅의 대표 항목이라 이 앱과 맞지 않는다.

## 각 기능의 모델 깊이

정직하게 적어둔다. 이 프로젝트가 실제로 판 건 **만세력 정확도 하나**다.

| 기능 | 모델 | 깊이 |
|---|---|---|
| **만세력 · 대운** | tzdata 표준시 이력 + 진태양시 + 절기 분 단위 + 대운수 + 순역 + **십이운성** | **깊음.** 골든 50건 + 십이운성 120조합 교차 검증 |
| **궁합** | 일간 오행 + 일지(육합·삼합·충·형) + 오행 보완 + 상호 십성 | 보통. 12자 전부 사용 |
| **신년** | 세운 십성 + **지금 대운과의 합충 관계** | 보통 |
| **원국 해석** | 궁위 + 오행 균형 + 지장간 + 공망 + 십이운성 + 신강신약·용신 + **신살 13종** | 보통. 여덟 자 전부 사용 |
| **오늘** | 일진 천간·지지 십성 + 십이운성 + 내 일지와의 합충 | 보통 |

### 십이운성을 대운에 넣은 이유

대운 칸이 간지와 십성만 보여주면 "그 10년에 무슨 일이 있나"는 알려주지만
"그때 내가 힘이 있었나"는 말해주지 않는다. 같은 편관 대운이어도 건록·제왕
자리면 밀어붙일 힘이 있고, 절·묘 자리면 버티는 시기가 된다.

각 칸에 막대로 표시한다. **점수가 아니다** — 십이운성 열두 자리를 길이로
옮긴 것이고, 절·묘가 짧은 건 나쁘다는 뜻이 아니라 밖으로 뻗는 힘이 약한
대신 안으로 여무는 시기라는 뜻이다. 그래서 변수 이름도 `strength` 가 아니라
`outwardness` 다.

표(10간 × 12지)는 직접 만들었고, `lunar-javascript` 가 원국 지지에 대해
주는 값과 **120개 조합에서 대조**해 검증한다. 표가 한 칸이라도 틀리면
테스트가 잡는다.

### 원국을 여덟 자 전부로 읽는다

원본은 십성 카테고리를 세어 가장 많은 하나(dominant)로 성격과 직업을
결정했다. 여덟 자를 계산해놓고 카운트 하나로 뭉갠 셈이다.

- **궁위** — 같은 관성도 년주면 집안의 규율이고 시주면 자식·말년의 책임이다.
  네 기둥이 각각 인생의 한 시기를 맡는다.
- **지장간** — 지지 속에 숨은 천간. 라이브러리가 배열로 주는데 `[0]`만 쓰고
  있었다. 월지는 셋까지 나온다.
- **공망** — 비어 있는 자리. 그 궁위의 일이 헛돌기 쉽다고 본다.
  라이브러리 `getDayXunKong()` 과 대조 검증한다.
- **오행 균형** — 없는 오행과 넘치는 오행(넷 이상). 화면에만 있고 해석
  문장에는 안 쓰이고 있었다.

### 용신 — 억부용신법을 쓰고, 그 사실을 밝힌다

명리에는 용신을 잡는 방법이 여럿이다 (억부·조후·병약·통관·전왕).
그중 실무에서 가장 널리 쓰이는 **억부용신법**을 쓴다. 일간이 강하면
눌러주고 약하면 도와주는 기운을 용신으로 본다.

**다른 방법을 쓰면 다른 답이 나온다.** 그래서 화면 맨 위에 "억부용신법
기준입니다. 조후·병약 등 다른 방법을 쓰면 답이 달라질 수 있습니다"를
적어둔다. 숨기고 정답인 척하는 것이 이 앱에서 가장 하면 안 되는 일이다.

**판정만 던지지 않는다.** "당신은 신강입니다"는 아무 도움이 안 된다.
득령·득지·득세를 각각 O/X 로 보여주고, 자리별 계산을 펼쳐볼 수 있게 한다.

```
월지 辰 편인 인성  +3     ← 태어난 계절의 기운이라 가장 무겁다
일지 午 정관 관성  -2
년지 午 정관 관성  -1.5
시지 辰 편인 인성  +1.5
월간 庚 비견 비겁  +1
년간 庚 비견 비겁  +1
시간 庚 비견 비겁  +1
                  ────
      돕는 7.5 / 빼는 3.5 → 68% → 신강
```

무게(월지 3, 일지 2, 년·시지 1.5, 천간 1)도 화면에 적어둔다. 사용자가
동의하지 않으면 어디가 다른지 짚을 수 있어야 한다.

#### 외부 정답지가 없는 것을 어떻게 검증하나

만세력은 골든 50건으로 교차 검증했지만 용신은 그럴 수 없다. 대신
**성질**로 검증한다. 어떤 판정법을 쓰든 반드시 지켜야 하는 것들이다.

1. 비겁·인성만으로 채운 명식은 반드시 신강 (점수 1.0)
2. 식상·재성·관성만으로 채운 명식은 반드시 신약 (점수 0.0)
3. 돕는 자리를 하나 늘리면 점수가 반드시 올라간다 (단조성, 8단계 검증)
4. 신강이면 빼는 기운이, 신약이면 돕는 기운이 용신이다
5. 같은 입력에 같은 결과 (난수 없음)

이 다섯이 깨지면 판정법이 무엇이든 틀린 것이다.

## MCP 서버 — 계산을 다른 AI에게 연다

이 프로젝트가 실제로 판 건 만세력 정확도 하나다. 화면은 한 사람이 자기
사주를 볼 때 쓰이지만, 계산 자체는 다른 AI가 도구로 부를 때 더 넓게 쓰인다.
그래서 엔진을 MCP 서버로 그대로 연다.

```bash
pnpm build:mcp        # dist-mcp/server.js 하나로 번들
pnpm mcp              # 개발 중에는 tsx 로 직접
```

등록:

```json
{
  "mcpServers": {
    "myeongri-seojae": {
      "command": "node",
      "args": ["/절대경로/dist-mcp/server.js"]
    }
  }
}
```

| 도구 | 하는 일 |
|---|---|
| `calculate_saju` | 사주팔자 + 일간·오행·십성 |
| `get_daeun_timeline` | 대운 10칸. 십성·십이운성 포함 |
| `analyze_natal` | 신강신약·용신·궁위·오행균형·신살 |
| `check_compatibility` | 두 사람 궁합 (점수 없음) |
| `get_fortune` | 오늘 일진 · 올해 세운 |
| `check_timezone_data` | 이 런타임의 tzdata 가 한국 표준시 이력을 아는가 |

### 다른 사주 MCP와 다른 점 — 근거를 같이 낸다

조사해본 다른 구현들은 결과만 준다. 여기서는 모든 응답에 계산 근거가 붙는다.

```json
"calculationBasis": {
  "standardOffsetMinutes": 510,
  "standardOffsetLabel": "UTC+8:30",
  "trueSolarOffsetMinutes": -2.09,
  "daylightSaving": false,
  "hourUnknown": false,
  "note": "한국은 표준자오선이 네 번 바뀌었고 …"
}
```

음력으로 물어보면 어느 양력 날짜로 옮겼는지도 함께 낸다.

```json
"lunarInput": { "year": 2017, "month": 5, "leapMonth": true, "day": 10 },
"resolvedSolarDate": "2017-07-03",
"lunarBasis": "한국천문연구원 음양력 기준(KST). 중국 음력(UTC+8)과는 …"
```

부르는 쪽이 이 값으로 결과를 신뢰하거나 반박할 수 있다. 1954~61년생은
구현마다 결과가 갈리는데, 근거가 없으면 어느 쪽이 맞는지 판단할 방법이 없다.
음력도 마찬가지다 — 2017년 윤5월은 중국 음력에 아예 없는 달이다.

`calculationBasis` 누락은 조용한 퇴행이다 — 결과값은 그대로인데 근거만
빠지면 이 서버의 존재 이유가 사라지면서 아무 테스트도 깨지지 않는다.
그래서 `test/mcp.test.ts` 는 도구 목록을 돌면서 전수로 확인한다.

### 기존 구현 조사 — hjsh200219/fortuneteller

같은 일을 하는 MCP가 이미 있다. 읽어보니 시간 처리를 **제대로 하려고 한**
드문 구현이었다. tzdata 를 실제로 참조해 당시 표준시를 구한다. 그런데 그
다음이 어긋난다.

- 진태양시 보정을 **135° 기준**으로 계산한 뒤, 그 결과를 다시 **당시
  표준시** 로 읽는다. 135°는 UTC+9 의 자오선이므로, 표준시가 UTC+9가
  아니었던 구간에서는 보정이 이중으로 들어간다. 1954~61년(UTC+8:30)과
  서머타임 구간에서 `당시표준시 − 9h` 만큼 어긋난다
- `calculateYearPillar` 가 `date.getFullYear()` 를 쓴다. 이건 실행 머신의
  로컬 타임존을 따르므로, 서버가 어디서 도는지에 따라 연주가 달라진다

여기서는 보정량을 상수로 두지 않고 **(당시 표준시 오프셋 − 경도/15h)** 로
매번 계산하고, 절기표가 UTC+8 기준이라는 사실에 맞춰 년주·월주는 UTC+8
필드로, 일주·시주는 진태양시 필드로 따로 뽑는다. 두 타임라인의 차이는
서울 기준 27분 55초다.

> 앞선 조사에서 이 구현이 −30분 고정 보정을 쓴다고 적었는데 그건 틀렸다.
> `TRUE_SOLAR_TIME_ADJUSTMENT = -30` 은 legacy 로 표시돼 있고 사주 계산에
> 쓰이지 않는다. 실제 문제는 위의 두 가지다.

## 절기 — 표가 아니라 천체력과 맞춘다

골든 50건은 만세력 라이브러리 **둘을 서로** 대조한다. 둘이 같은 절기표
계보를 물려받았다면 둘 다 틀려도 서로 맞다고 한다. 표를 또 다른 표와
맞춰보는 것으로는 그 경우를 못 걸러낸다.

그래서 방법 자체를 바꿨다. 절기는 원래 표에서 찾는 것이 아니라 **태양의
겉보기 황경이 15° 배수에 닿는 순간**으로 정의된다. `astronomy-engine`
(VSOP87 기반 천체력)으로 그 순간을 직접 푼다. 표 대 표가 아니라 표 대 천체력이다.

### 이 프로젝트가 서 있는 가정

년주·월주는 UTC+8 필드로 뽑고 일주·시주는 진태양시 필드로 뽑는다
(`src/core/manse.ts`). lunar-javascript 의 절기표가 UTC+8 기준이기 때문이다.
**이 가정이 틀리면 절기 경계에 걸린 모든 사람의 년주·월주가 틀린다.**

1900~2050년 × 24절기 = **3,624 표본**을 대조했다.

| 가설 | 결과 |
|---|---|
| 절기표 = UTC+8 | **최대 편차 55.8초** — 전 표본 1분 이내 |
| 절기표 = UTC+9 | 평균 편차 3,601초 = 정확히 한 시간 |

맞는 가설만 맞는다. 1957년 입춘으로 보면:

```
lunar-javascript 표          1957-02-04 09:54:37
천체력 (황경 315° 직접 계산)  1957-02-04 09:54:42   (UTC+8)
                                        └ 5초 차
```

### 표가 맞는 것과 우리가 제대로 쓰는 것은 다른 문제다

그래서 한 단계 더 간다. 천체력이 준 입춘 순간을 **그 시절 한국 표준시**
벽시계로 옮긴 뒤, 1분 30초 전과 후로 사주를 뽑아 년주가 실제로 갈리는지
본다. 갈리는 방향(60갑자에서 정확히 한 칸)까지 확인한다. 표준시가 UTC+9가
아니던 해(1957, 1960, 1961)와 서머타임 해(1948, 1988)를 일부러 넣었다.

이 테스트에 이빨이 있는지도 확인했다. `manse.ts` 에서 년주를 진태양시 필드로
뽑도록 한 줄 바꿔보면 — 절기표를 KST로 오해한 것과 같은 상태 — **10개
테스트가 죽는다.** 잡으라고 만든 걸 실제로 잡는다.

`astronomy-engine` 은 devDependency다. 번들에 새어 들어가지 않는지
`bundle.test.ts` 가 모든 청크를 확인한다.

## 한국 음력 ≠ 중국 음력 — 작업 중에 찾은 진짜 버그

일주 검증을 하러 갔다가 더 큰 걸 밟았다.

### 음력 달은 삭이 드는 "날" 에 시작한다

"순간" 이 아니라 "날" 이다. 그래서 삭(朔, 신월)이 자정 근처에 들면 어느
시간대로 읽느냐에 따라 달의 시작이 하루 갈린다. 중국 음력은 UTC+8,
한국 음력(한국천문연구원)은 KST 로 읽는다.

**1900~2050 삭 1,868회 중 67회(3.6%)가 두 기준에서 다른 날짜다.**

```
1914년 윤5월 삭
  UTC+8   1914-06-23 23:33:24   → 중국은 6월 23일에 달이 시작
  KST     1914-06-24 00:33:24   → 한국은 6월 24일에 달이 시작
```

하루가 어긋나면 **일주가 통째로 바뀐다.**

### 더 큰 것 — 윤달이 한 달 옮겨간다

윤달은 中氣(중기)가 없는 달인데, 中氣 역시 "날" 로 판정한다.

```
2017년 대서(大暑)
  UTC+8   2017-07-22 23:15:23   → 中氣가 앞 달에 속함  → 그 달은 평6월, 다음이 윤6월
  KST     2017-07-23 00:15:23   → 中氣가 뒷 달에 속함  → 앞 달이 中氣 없음 → 윤5월
```

한 시간 차이로 **윤달이 통째로 한 달 옮겨간다.** 한국 달력은 2017년을
윤5월로, 중국 달력은 윤6월로 적는다.

### 어느 라이브러리도 믿지 않고 규칙을 직접 구현했다

"korean-lunar-calendar 가 한국 것이겠지" 로 넘어가면 검증이 아니다.
천체력으로 삭과 中氣의 순간을 구한 뒤, 각 시간대의 **날짜**로 달을 매기는
규칙을 그대로 구현해서 대조했다.

> 달은 삭이 드는 날에 시작한다 · 中氣가 든 날로 달 번호를 정한다 ·
> 동지가 든 달이 11월이다 · 동지에서 동지까지 13달이면 中氣 없는 첫 달이 윤달이다

| 라이브러리 | UTC+8 규칙 | KST 규칙 |
|---|---|---|
| lunar-javascript | **99.78%** | 96.13% |
| korean-lunar-calendar | 96.74% | **99.50%** |

lunar-javascript 는 중국 음력, korean-lunar-calendar 는 한국 음력이다.
korean-lunar-calendar 가 어긋나는 건 전부 **1911년 이전** — 한국이 표준시를
정하기 전 구간이다.

### 우리는 중국 음력을 쓰고 있었다

사용자가 넣는 음력은 가족관계등록부에 적힌 **한국 음력**이다. 그걸 중국
음력 표로 옮기고 있었다. 증상은 두 가지였다.

- **하루 어긋남** — 음력 입력의 3.4% 에서 다른 양력 날짜로 옮겨졌다.
  일주가 통째로 바뀐다
- **아예 거절** — 2017년 윤5월은 중국 달력에 존재하지 않는다. 한국 달력에
  윤5월로 적힌 대로 넣은 사람은 "그 해에는 윤달이 없습니다" 를 봤다

고쳤다. 음↔양 변환만 한국 기준으로 넘기고, 절기와 간지는 UTC+8 표가
맞다는 걸 이미 검증했으므로 그대로 둔다.

```
음↔양 변환   한국 기준  (core/korean-lunar.ts)
절기 · 간지   UTC+8 표   (core/manse.ts)
```

이 갈라놓기가 이 프로젝트의 두 타임라인 구조와 같은 결이다. 그리고
리포트에 **어느 양력 날짜로 옮겼는지** 적는다 — 다른 곳과 결과가 다를 때
어디서 갈렸는지 짚을 수 있어야 한다.

> 음력 2017년 5월 10일 윤달 · 시간 미상
> 양력 2017년 7월 3일로 계산했습니다 · 한국천문연구원 음양력 기준

2050년까지가 한국 자료의 범위다. 그 뒤로는 중국 음력으로 물러나고,
`supportsKoreanLunar()` 가 그 경계를 알려준다.

## 일주 — 율리우스일로 검증한다

일주는 끊기지 않는 60갑자 순환이다. 그래서 **율리우스일(JDN)로 직접**
검증할 수 있다. 그레고리력 날짜에서 JDN 을 구하고, 상수 하나로 60갑자
인덱스가 나오는지 본다.

**1900~2100년 73,414일 전부, 상수 하나(k=49)가 모든 날을 설명한다.**
윤년·세기 경계·그레고리력 어디에서도 어긋나는 날이 없다.

구조 규칙도 같이 확인했다. 골든 50건이 드문드문 훑는 영역이라 전수로 본다.

| 규칙 | 검증 |
|---|---|
| 오호둔(五虎遁) — 년간이 인월 천간을 정한다 | 1,452건 불일치 0 |
| 오자시두법(五鼠遁) — 일간이 자시 천간을 정한다 | 9,720건 불일치 0 |

## 대운수 — 마지막 남은 구멍이었다

사주팔자는 절기·율리우스일로, 음력은 규칙으로 판정했는데 **대운수는
라이브러리 값을 그대로 받아 쓰면서 그 숫자를 확인하지 않고 있었다.**
기존 테스트는 방향(순행·역행)과 단조성 같은 **구조**만 봤다. 숫자 자체는
아무도 안 봤다.

대운수가 1년 틀리면 타임라인이 10년씩 밀리는 게 아니라 1년씩 밀린다.
눈에 잘 안 띄고, 그래서 더 조용히 틀린다.

규칙은 이렇다 — 순행이면 태어난 순간부터 **다음 절입**까지, 역행이면
**직전 절입**부터 태어난 순간까지, 그 일수를 3으로 나눈다(3일 = 1년).
절입은 달을 여는 절기(節氣) 12개이지 중기(中氣)가 아니다.

천체력으로 그 절입 순간을 직접 구해 대조했다. **408건 최대차 0.0385년.**
남는 차이는 오차가 아니라 라이브러리가 결과를 전통 단위(몇 년 몇 월 며칠)로
반올림한 잔차다 — 반 달치 안쪽이다.

돌연변이 검사도 했다. 3 대신 4로 나누면 3개, 순행·역행을 뒤집으면 2개가
죽는다.

## 결과 링크 공유 — 정직한 절충

서버가 없다. 그러니 링크로 결과를 복원하려면 **링크 안에 입력이 들어 있어야
한다.** 이건 암호화가 아니다. 링크를 받은 사람은 생년월일시를 되읽을 수 있고,
되읽을 수 있어야 링크가 작동한다. 그래서 버튼 밑에 그대로 적었다.

> 링크에는 생년월일이 글자로 들어가지 않지만,
> **링크를 가진 사람은 이 사주를 그대로 볼 수 있습니다.**

그럼 왜 `?year=1990&month=5` 로 안 하는가. 막으려는 게 다른 것이기 때문이다 —
**지나가다 읽히는 것**이다. 주소창과 방문 기록, 채팅 미리보기, 오류 리포트.

| 결정 | 이유 |
|---|---|
| 쿼리가 아니라 **프래그먼트(#)** | 서버로 전송되지 않고 Referer 에도 안 실린다. 정적 호스팅 로그에 안 남는다 |
| 비트로 접어 base64url | `#r=E5VxS8AA-Ts` — 11글자. 어깨너머로 안 읽히고, 채팅에서 안 잘린다 |
| 체크섬 **16비트** | 8비트면 손상된 링크가 256분의 1로 통과한다. 통과하면 조용히 *다른 사람 사주*가 나온다 |
| 표준형 검사 | base64 마지막 글자의 잉여 비트만 바뀐 토큰은 체크섬이 못 잡는다. 다시 접어 원본과 대조해 모든 글자가 의미를 갖게 했다 |
| 이름은 안 담는다 | 누구 것인지가 붙는 순간 성질이 달라진다 |

토큰 전 위치 × 전 글자로 한 글자씩 바꿔보는 전수 검사에서 **통과하는 변형이
하나도 없다.** 잘린 링크는 반드시 실패하고, 실패하면 이렇게 말한다 —
"링크가 손상됐습니다. 메신저에서 주소 뒤가 잘렸을 수 있어요."

### 여기서 실제 구멍이 하나 나왔다

원래 설계는 "URL 해시를 아예 쓰지 않는다" 였다. Sentry 가 `location.href` 를
이벤트에 담기 때문이다. 이제 해시를 쓰기로 했으니 세탁이 되는지 확인하는
테스트를 먼저 썼는데 — **브레드크럼에서 실패했다.** `scrubUrl` 은 프래그먼트를
버리지만, navigation 브레드크럼의 `to`/`from` 은 `scrubDeep` 을 거쳐 날짜만
지워지고 있었다. 토큰은 날짜처럼 안 생겼으니 그대로 남았다.

`scrubDeep` 이 URL 처럼 생긴 문자열을 URL 로 세탁하도록 고쳤다.

## 인생 대조표 — 맞다고 말해주는 대신 직접 적게 한다

각 대운 칸을 펼치면 글 쓰는 칸이 있다. 지나온 10년에는 이렇게 묻는다.

> **1967~1976년, 실제로 무슨 일이 있었나요**
> 이직, 이사, 만남, 아팠던 일…

앞으로 올 10년에는 묻지 않는다. "무슨 일이 있었나요" 를 미래에 물으면 그건
예언을 받아적으라는 뜻이 되어버린다.

적은 것은 리포트에도 실린다 — 사주 풀이 옆에 본인이 겪은 일이 나란히 놓인다.
이 문서에서 유일하게 우리가 쓰지 않은 부분이고, 그게 이 기능의 요점이다.

저장은 이 기기의 localStorage 뿐이다. 저장 키에도 생년월일이 평문으로 들어가지
않게 공유 토큰과 같은 불투명 키를 쓴다. 다른 사람 사주로 넘어가면 그 사람의
칸은 비어 있고, 지우기 버튼은 **이 사주의 기록만** 지운다.

곁가지로 잡힌 것: `restoreSaved` 가 정의만 되어 있고 **어디서도 호출되지
않고 있었다.** 저장만 하고 복원을 안 하던 셈이다. 부팅 경로를 만들면서 같이
연결했다 — 링크가 있으면 링크로, 없으면 마지막 입력을 폼에만 채운다(자동
계산은 안 한다. 남의 기기에서 열었을 때 남의 사주가 튀어나오면 곤란하다).

## 아직 안 한 것

- **KASI 공식 대조** — 절기는 천체력으로 직접 검증했다(위 "절기" 절). 그 위에
  공식 기관 값까지 맞춰보는 건 `pnpm verify:kasi` 로 남겨뒀는데,
  공공데이터포털 키 발급이 사람 손을 타는 절차라 아직 실키로 못 돌려봤다.
  응답 형태를 문서로만 보고 맞췄으므로 처음 돌릴 때 `--raw` 로 확인이 필요하다
- **1911년 이전 음력** — 한국 음력 자료가 그 구간에서 KST 규칙과 여덟 번
  어긋난다. 대한제국이 표준시를 정하기 전이라 어느 기준이 맞는지부터
  정해야 한다. 1900~1911년생은 지금도 계산되지만 음력 입력의 정밀도가
  그 뒤 구간보다 낮다
