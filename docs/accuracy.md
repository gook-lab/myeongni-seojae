# 만세력 정확도

> 이 프로젝트가 판 것은 정확도 하나예요. 여기 있는 내용이 그 근거예요.

[← 명리서재](../README.md)

## 이 프로젝트가 실제로 고친 것

만세력이 어렵다고 하면 사람들은 절기 천문 계산을 떠올려요. **틀렸어요.** 절기 계산은
이미 라이브러리가 풀어놨어요. 앱마다 사주 결과가 갈리는 진짜 이유는 **한국 표준시
변경 이력**이에요. 천문학이 아니라 행정 데이터거든요.

한국은 표준자오선이 네 번 바뀌었고 서머타임도 세 시기 있었어요. 그래서 시계 시각을
진태양시로 바꾸는 보정량은 **상수가 아니에요.**

| 시계 기준 | 보정량 | 해당 구간 |
|---|---|---|
| UTC+9:00 | −32분 05초 | 1912~54, 1961~현재 |
| UTC+8:30 | **−2분 05초** | 1954~61 겨울 |
| UTC+9:30 | −62분 05초 | 1954~61 서머타임 |
| UTC+10:00 | −92분 05초 | 1987~88 서머타임 |

흔한 오구현은 "서울 126.978°E, 표준자오선 135°E → −32분"을 상수로 박는 거예요.
그러면 1954~61년생 시주가 30분 어긋나요. 시주는 2시간 단위라 경계 ±30분 출생자가
통째로 오답이 돼요. 부모님 세대가 정확히 그 구간이거든요.

### 실제로 갈리는 예

npm에 배포된 만세력 라이브러리 `manseryeok`과 대조한 결과예요.

```
1957-02-04, 실제 한국 표준시 UTC+8:30
  입춘(UTC 01:55)을 당시 시계로 읽으면 KST 10:25:00
  출생 KST 10:30 → 입춘 이후

  명리서재     丁酉 壬寅   ✓
  manseryeok  丙申 辛丑   ✗  (KST=UTC+9 로 고정 가정)
```

년주와 월주가 **둘 다** 달라요. 같은 사람인데 완전히 다른 사주가 나와요.

### 해법 — 시대 분기를 없애요

```
1) 시계시각 + 'Asia/Seoul'  →  UTC        [IANA tzdata 가 전담]
2) UTC + 경도/15h           →  진태양시    [시대와 무관한 상수 하나]
```

두 지점 사이에 시대별 표를 손으로 들고 있을 이유가 없어요. tzdata가 이미 갖고 있고,
위 네 보정량은 이 공식에서 자동으로 도출돼요. 손으로 쓴 표는 서머타임 시행 날짜를
틀리지만 tzdata는 안 틀려요.

검증 (Node v24, `Intl` + `Asia/Seoul`):

| 날짜 | 실측 | 구간 |
|---|---|---|
| 1910-06-15 | GMT+08:30 | 대한제국기 |
| 1930-06-15 | GMT+09:00 | 일제강점기 |
| 1957-06-15 | GMT+09:30 | UTC+8:30 + 서머타임 |
| 1957-12-15 | GMT+08:30 | UTC+8:30 겨울 |
| 1987-07-15 | GMT+10:00 | 1987 서머타임 |
| 1990-08-15 | GMT+09:00 | 현재 |

## 뼈대도 우리 알고리즘으로 — 사주팔자를 직접 세워요

지적을 받았어요. 해석(대운·십이운성·용신·신살·궁합)은 우리 알고리즘인데
**정작 뼈대인 사주팔자는 라이브러리 위임**이었거든요. 해석이 아무리 좋아도
뼈대가 남의 블랙박스면 "우리 알고리즘"이라 말하기 어렵잖아요.

그런데 지금은 사정이 달라요. 그 라이브러리가 쓰는 규칙을 이미 전부 독립
검증해뒀거든요. **검증한 규칙이 곧 구현할 규칙이에요.**

| 필요한 것 | 이미 검증해둔 것 |
|---|---|
| 절기 | 천체력으로 황경 직접 계산 · 3,624 표본 |
| 일주 | 율리우스일 + 상수 하나 · 73,414일 |
| 월주 천간 | 오호둔(五虎遁) · 1,452건 |
| 시주 천간 | 오자시두법(五鼠遁) · 9,720건 |

### 절기표를 우리가 만들어요

브라우저에서 천체력을 돌리기엔 무거워요. `pnpm gen:terms`가 미리 뽑아
표로 만들어요 — 만드는 코드가 검증에 쓴 코드와 같아요. 1900~2100년 × 24절기
= 4,824개를 델타 + 36진수로 접어 **23.6KB**.

값은 벽시계가 아니라 **UTC 순간**이에요. 절기는 순간이니까 출생의 순간과
곧바로 견주면 되고, 그러면 "어느 시간대의 벽시계인가"를 따질 필요가 없어요.

초를 버리면 안 되는데, 처음엔 분으로 반올림했다가 1977년 입추(23:30:25)가
23:30:00이 되면서, **23시 30분에 태어난 사람이 경계 위에 얹혀 월주가 한 칸
어긋났어요.** 한 글자 더 쓰고 그 사고를 없앴어요.

### 결과 — 관계가 뒤집혀요

`src/core/pillars.ts`가 네 기둥을 직접 세워요. 1901~2099년 표본으로 대조:

| | 결과 |
|---|---|
| 년주 · 월주 · 일주 · 시주 | **1,791건 불일치 0** |
| 지장간 12지 | 불일치 0 |
| 공망 (표 없이 순旬에서 계산) | 102건 불일치 0 |
| 대운 순행·역행 | 불일치 0 |
| 대운 간지 10칸 | 불일치 0 |
| 대운 시작 나이 | 99.1% 일치 |

이제 lunar-javascript는 **계산의 근거가 아니라 대조 상대**예요. 같은 표를
물려받은 둘이 서로 맞다고 하는 상황이 아니라, 방법이 다른 둘이 맞춰보는
상황이에요.

### 남은 0.9%는 숨기지 않아요

대운 시작 나이만 1%가 안 되게 갈려요. 대운수(절입까지 일수 ÷ 3)라는 규칙은
같은데 **나머지를 어떻게 끊느냐**가 달라요. 옛 계산법은 나머지를 시진(두
시간)으로 끊고 한 시진을 열흘로 치는데, 우리는 전체를 한 번에 끊고
라이브러리는 중간 단계마다 다르게 끊어요.

한 살 차이라 무시할 것은 아니지만 어느 쪽이 옳다고 말할 근거가 없는
자리예요. 그래서 테스트에 수치로 적어뒀어요.

### 갈아끼웠어요 — 엔진 청크가 4분의 1로

런타임에서 lunar-javascript가 **완전히 사라졌어요.** `src/` 어디에도 그
라이브러리를 값으로 import 하는 곳이 없어요.

```
엔진 청크   382.14KB → 100.42KB   (gzip 127.44 → 40.99KB)
```

계산 라이브러리 300KB를 걷어낸 자리에 우리 절기표 23.6KB가 들어갔어요.
느린 회선의 부모님 세대에게는 이 차이가 몇 초니까요.

바뀐 것은 딱 하나 — 대운 시작 나이가 골든 54건 중 한 건에서 한 살
달라졌어요(1987-07-15). 대운수 2.44년을 세는나이로 옮기면 3세인데
라이브러리는 4세로 봤거든요. 우리 값이 규칙에 더 충실해요.

음력도 정직해졌어요. 2050년을 넘으면 예전에는 중국 음력으로 조용히
물러났는데, 그건 하루 어긋난 값을 아무 말 없이 내주는 거라 **거절**로
바꿨어요. 못 하는 것은 못 한다고 말해요.

이제 lunar-javascript는 devDependency예요. 테스트에서 대조 상대로만 써요.

## 절기 — 표가 아니라 천체력과 맞춰요

골든 54건은 만세력 라이브러리 **둘을 서로** 대조해요. 둘이 같은 절기표
계보를 물려받았다면 둘 다 틀려도 서로 맞다고 말해요. 표를 또 다른 표와
맞춰보는 것으로는 그 경우를 못 걸러내요.

그래서 방법 자체를 바꿨어요. 절기는 원래 표에서 찾는 것이 아니라 **태양의
겉보기 황경이 15° 배수에 닿는 순간**으로 정의돼요. `astronomy-engine`
(VSOP87 기반 천체력)으로 그 순간을 직접 풀어요. 표 대 표가 아니라 표 대 천체력이에요.

### 이 프로젝트가 서 있는 가정

년주·월주는 UTC+8 필드로 뽑고 일주·시주는 진태양시 필드로 뽑아요
(`src/core/manse.ts`). lunar-javascript의 절기표가 UTC+8 기준이기 때문이에요.
**이 가정이 틀리면 절기 경계에 걸린 모든 사람의 년주·월주가 틀려요.**

1900~2050년 × 24절기 = **3,624 표본**을 대조했어요.

| 가설 | 결과 |
|---|---|
| 절기표 = UTC+8 | **최대 편차 55.8초** — 전 표본 1분 이내 |
| 절기표 = UTC+9 | 평균 편차 3,601초 = 정확히 한 시간 |

맞는 가설만 맞아요. 1957년 입춘으로 보면:

```
lunar-javascript 표          1957-02-04 09:54:37
천체력 (황경 315° 직접 계산)  1957-02-04 09:54:42   (UTC+8)
                                        └ 5초 차
```

### 표가 맞는 것과 우리가 제대로 쓰는 것은 다른 문제예요

그래서 한 단계 더 가요. 천체력이 준 입춘 순간을 **그 시절 한국 표준시**
벽시계로 옮긴 뒤, 1분 30초 전과 후로 사주를 뽑아 년주가 실제로 갈리는지
봐요. 갈리는 방향(60갑자에서 정확히 한 칸)까지 확인해요. 표준시가 UTC+9가
아니던 해(1957, 1960, 1961)와 서머타임 해(1948, 1988)를 일부러 넣었어요.

이 테스트에 이빨이 있는지도 확인했어요. `manse.ts`에서 년주를 진태양시 필드로
뽑도록 한 줄 바꿔보면 — 절기표를 KST로 오해한 것과 같은 상태 — **10개
테스트가 죽어요.** 잡으라고 만든 걸 실제로 잡아요.

`astronomy-engine`은 devDependency예요. 번들에 새어 들어가지 않는지
`bundle.test.ts`가 모든 청크를 확인해요.

## 한국 음력 ≠ 중국 음력 — 작업 중에 찾은 진짜 버그

일주 검증을 하러 갔다가 더 큰 걸 밟았어요.

### 음력 달은 삭이 드는 "날"에 시작돼요

"순간"이 아니라 "날"이거든요. 그래서 삭(朔, 신월)이 자정 근처에 들면 어느
시간대로 읽느냐에 따라 달의 시작이 하루 갈려요. 중국 음력은 UTC+8,
한국 음력(한국천문연구원)은 KST로 읽어요.

**1900~2050 삭 1,868회 중 67회(3.6%)가 두 기준에서 다른 날짜예요.**

```
1914년 윤5월 삭
  UTC+8   1914-06-23 23:33:24   → 중국은 6월 23일에 달이 시작
  KST     1914-06-24 00:33:24   → 한국은 6월 24일에 달이 시작
```

하루가 어긋나면 **일주가 통째로 바뀌어요.**

### 더 큰 것 — 윤달이 한 달 옮겨가요

윤달은 中氣(중기)가 없는 달인데, 中氣 역시 "날"로 판정해요.

```
2017년 대서(大暑)
  UTC+8   2017-07-22 23:15:23   → 中氣가 앞 달에 속함  → 그 달은 평6월, 다음이 윤6월
  KST     2017-07-23 00:15:23   → 中氣가 뒷 달에 속함  → 앞 달이 中氣 없음 → 윤5월
```

한 시간 차이로 **윤달이 통째로 한 달 옮겨가요.** 한국 달력은 2017년을
윤5월로, 중국 달력은 윤6월로 적어요.

### 어느 라이브러리도 믿지 않고 규칙을 직접 구현했어요

"korean-lunar-calendar가 한국 것이겠지"로 넘어가면 검증이 아니니까,
천체력으로 삭과 中氣의 순간을 구한 뒤, 각 시간대의 **날짜**로 달을 매기는
규칙을 그대로 구현해서 대조했어요.

> 달은 삭이 드는 날에 시작한다 · 中氣가 든 날로 달 번호를 정한다 ·
> 동지가 든 달이 11월이다 · 동지에서 동지까지 13달이면 中氣 없는 첫 달이 윤달이다

| 라이브러리 | UTC+8 규칙 | KST 규칙 |
|---|---|---|
| lunar-javascript | **99.78%** | 96.13% |
| korean-lunar-calendar | 96.74% | **99.50%** |

lunar-javascript는 중국 음력, korean-lunar-calendar는 한국 음력이에요.
korean-lunar-calendar가 어긋나는 건 전부 **1911년 이전** — 한국이 표준시를
정하기 전 구간이에요.

### 우리는 중국 음력을 쓰고 있었어요

사용자가 넣는 음력은 가족관계등록부에 적힌 **한국 음력**이거든요. 그걸 중국
음력 표로 옮기고 있었어요. 증상은 두 가지였어요.

- **하루 어긋남** — 음력 입력의 3.4%에서 다른 양력 날짜로 옮겨졌어요.
  일주가 통째로 바뀌니까요
- **아예 거절** — 2017년 윤5월은 중국 달력에 존재하지 않아요. 한국 달력에
  윤5월로 적힌 대로 넣은 사람은 "그 해에는 윤달이 없습니다"를 봤어요

고쳤어요. 음↔양 변환만 한국 기준으로 넘기고, 절기와 간지는 UTC+8 표가
맞다는 걸 이미 검증했으니까 그대로 둬요.

```
음↔양 변환   한국 기준  (core/korean-lunar.ts)
절기 · 간지   UTC+8 표   (core/manse.ts)
```

이 갈라놓기가 이 프로젝트의 두 타임라인 구조와 같은 결이에요. 그리고
리포트에 **어느 양력 날짜로 옮겼는지** 적어요 — 다른 곳과 결과가 다를 때
어디서 갈렸는지 짚을 수 있어야 하거든요.

> 음력 2017년 5월 10일 윤달 · 시간 미상
> 양력 2017년 7월 3일로 계산했습니다 · 한국천문연구원 음양력 기준

2050년까지가 한국 자료의 범위예요. 그 뒤로는 중국 음력으로 물러나고,
`supportsKoreanLunar()`가 그 경계를 알려줘요.

## 일주 — 율리우스일로 검증해요

일주는 끊기지 않는 60갑자 순환이에요. 그래서 **율리우스일(JDN)로 직접**
검증할 수 있어요. 그레고리력 날짜에서 JDN을 구하고, 상수 하나로 60갑자
인덱스가 나오는지 봐요.

**1900~2100년 73,414일 전부, 상수 하나(k=49)가 모든 날을 설명해요.**
윤년·세기 경계·그레고리력 어디에서도 어긋나는 날이 없어요.

구조 규칙도 같이 확인했어요. 골든 54건이 드문드문 훑는 영역이라 전수로 봐요.

| 규칙 | 검증 |
|---|---|
| 오호둔(五虎遁) — 년간이 인월 천간을 정한다 | 1,452건 불일치 0 |
| 오자시두법(五鼠遁) — 일간이 자시 천간을 정한다 | 9,720건 불일치 0 |

## 대운수 — 마지막 남은 구멍이었어요

사주팔자는 절기·율리우스일로, 음력은 규칙으로 판정했는데 **대운수는
라이브러리 값을 그대로 받아 쓰면서 그 숫자를 확인하지 않고 있었어요.**
기존 테스트는 방향(순행·역행)과 단조성 같은 **구조**만 봤거든요. 숫자 자체는
아무도 안 봤어요.

대운수가 1년 틀리면 타임라인이 10년씩 밀리는 게 아니라 1년씩 밀려요.
눈에 잘 안 띄고, 그래서 더 조용히 틀려요.

규칙은 이래요 — 순행이면 태어난 순간부터 **다음 절입**까지, 역행이면
**직전 절입**부터 태어난 순간까지, 그 일수를 3으로 나눠요(3일 = 1년).
절입은 달을 여는 절기(節氣) 12개이지 중기(中氣)가 아니에요.

천체력으로 그 절입 순간을 직접 구해 대조했어요. **408건 최대차 0.0385년.**
남는 차이는 오차가 아니라 라이브러리가 결과를 전통 단위(몇 년 몇 월 며칠)로
반올림한 잔차거든요 — 반 달치 안쪽이에요.

돌연변이 검사도 했어요. 3 대신 4로 나누면 3개, 순행·역행을 뒤집으면 2개가
죽어요.

## 파이썬 — 옮기는 게 아니라 네 번째 시선으로

"파이썬으로 넣어둬야 완벽하지 않나"는 물음에 대한 답이에요.

**런타임을 파이썬으로 옮기면 서버가 필요하고, 서버가 생기면 생년월일이
기기를 떠나요.** 이 프로젝트의 프라이버시 구조 전체가 "아무것도 나가지
않는다"위에 서 있거든요 — Sentry 세탁, URL에 날짜 안 넣기, localStorage만
쓰기, 공유 링크의 불투명 토큰이 전부 그래서 있어요. 정확도 때문이라면
파이썬이 나을 이유도 없어요.

그런데 **검증 도구로는 값어치가 크거든요.** 지금까지 대조 상대는 넷이었는데
**넷 다 자바스크립트 생태계 안에 있었어요.** 같은 생태계의 같은 관습을
공유하면 같은 착각도 공유할 수 있으니까요.

`verify/reference.py`는 다른 언어에서, 다른 천체력으로, 다른 저자의
자료로 **처음부터 다시** 계산해요. 우리 코드를 옮겨 적은 게 아니라
규칙만 보고 새로 썼거든요.

| | 우리 (TS) | 파이썬 |
|---|---|---|
| 천체력 | astronomy-engine (VSOP87 계열) | **skyfield / JPL DE421** |
| 절기 | 미리 뽑은 표 | 그 자리에서 이분법으로 탐색 |
| 일주 위상 | 상수 49 | **스스로 도출** |
| 음력 | korean-lunar-calendar (JS) | korean_lunar_calendar (Python) |

일주 위상 상수를 물려주지 않는 게 요점이에요. 파이썬 쪽은 "1949년 10월
1일이 갑자일"이라는 사실 하나에서 스스로 구하는데, **그 값이 49로
나와요.** 우리가 73,414일로 확인한 그 값이거든요.

```
$ pnpm verify:python 150

일주 위상 상수 — 우리 49 · 파이썬 49 ✓
대조 150건
  년주 0 · 월주 0 · 일주 0 · 시주 0
전부 일치해요.
```

CI에는 넣지 않아요. 천체력 파일 17MB와 파이썬 환경이 필요해서 배포
게이트에 매달 일이 아니거든요 — 손으로 돌리는 확인이에요.
