## 설계 결정

| 결정 | 이유 |
|---|---|
| **시간 미상이 기본 입력** | 관객이 부모님 세대다. 태어난 시각을 모르는 게 정상이지 예외가 아니다. 그리고 **대운 타임라인은 시주를 참조하지 않아** 시각 없이도 100% 정확하다 |
| **점수를 전부 없앰** | 기존 구현은 `Math.sin`으로 운세 점수를 만들고 있었다. 명리에 정설화된 점수법이 없으므로 새 산식을 만드는 것도 근거 없는 숫자를 포장하는 것이다. 텍스트만 남겼다 |
| **URL에 생년월일 없음** | Sentry가 `location.href`를 이벤트에 담는다. 다시보기는 localStorage만 쓴다 |
| **React Query 미사용** | 서버 상태가 0개다. 쿼리할 서버가 없는데 서버 상태 캐시를 둘 이유가 없다 |
| **계산 라이브러리 지연 로드** | 입력 화면을 보는 데 계산 코드가 필요 없다. 구형 안드로이드 + 느린 회선이 관객이다 |

## 구조

```
src/
  core/           순수 함수. React·Zustand·Sentry 를 import 하지 않는다
    korea-time.ts   ★심장★ 두 타임라인 + tzdata 런타임 자가진단
    manse.ts        사주 원국. 라이브러리를 두 번 호출한다 (아래 참조)
    daeun.ts        대운 타임라인. 시주를 참조하지 않는 것이 계약이다
    input.ts        검증 + 음양력. 예외를 던지지 않고 SajuResult 를 반환
    errors.ts       SajuError 유형
    regions.ts      출생지 경도
  text/           데이터만. 계산 로직 없음
    interpret.ts    카테고리별 단일 테이블
    daeun-text.ts   십성 10종 대운 문단
  engine/         동적 import 대상. lunar-javascript 와 텍스트를 여기서 끌고 온다
  ui/             상태와 부수효과를 아는 유일한 계층
  observability/  Sentry PII 차단
```

### 왜 라이브러리를 두 번 호출하는가

`lunar-javascript`의 절기표는 **UTC+8 기준**으로 계산돼 있다
(검증: 1957 입춘 = `1957-02-04 09:54:37` CST).

- **년주·월주**는 "출생 순간이 절기 순간보다 앞이냐 뒤냐"로 정해진다. 두 순간의
  비교이므로 같은 타임라인에 올려놓기만 하면 되고, 경도 보정분은 양변에서 상쇄된다.
  → 출생시각을 UTC+8로 읽어서 준다 (`cstFields`)
- **시주·일주**는 "해가 하늘 어디에 있었나"이므로 진태양시여야 한다.
  → `solarFields`

두 필드는 27분 55초 차이가 난다. 절기 경계 ±28분에 태어난 사람에게 실제로 다른
결과를 준다. 그래서 한 번 호출로 뭉개지 않는다.

## 배포 게이트

두 가지가 통과해야만 배포한다. 둘 다 **사람이 눈으로 못 잡는 종류의 실패**다.

**1. 골든 테스트** — 만세력이 조용히 틀리는 것을 막는다.
50건의 명식을 스냅샷으로 고정하고, 독립 구현(`manseryeok` v2)과 교차 대조한다.
갈리는 자리는 전부 이유가 분류돼 있어야 하며 `unexplained`가 하나라도 나오면 실패다.

```
true-solar-time        16건  경도 보정 유무 (규약 차이)
yajasi                  5건  23시대 시두 유파 (규약 차이)
standard-time-history   2건  manseryeok 이 틀리는 자리
```

**2. 프라이버시 게이트** — 생년월일이 Sentry로 새는 것을 막는다.
`location.href` / Session Replay / breadcrumbs / error context 네 경로를 전부 막고,
막혔는지를 테스트가 확인한다. 설정은 언제든 실수로 풀릴 수 있어서 테스트가 본체다.

CI는 러너의 tzdata가 한국 표준시 이력을 아는지부터 확인한다. ICU가 빈약하면 골든이
통째로 거짓 통과할 수 있기 때문이다.

## 개발

```bash
pnpm install
pnpm dev              # 개발 서버
pnpm test             # 단위 테스트
pnpm test:e2e         # E2E (모바일 + 데스크톱)
pnpm test:all         # 타입체크 + 빌드 + 전체 테스트
pnpm golden:gen       # 골든 정답지 재생성
```

**골든 정답지를 갱신할 때는 diff를 반드시 눈으로 확인할 것.** 테스트가 통과한다는
것은 "예전과 같다"는 뜻이지 "맞다"는 뜻이 아니다.
