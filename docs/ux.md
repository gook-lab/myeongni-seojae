# 화면과 움직임

> 관객이 부모님 세대다. 그 전제가 화면의 거의 모든 결정을 정했다.

[← 명리서재](../README.md)

## 첫 화면 — 메뉴 앞에 한 장

원래는 접속하자마자 메뉴였다. 그런데 첫 방문자가 보는 것이 **잠긴 버튼
세 개**였다 — 오늘·궁합·신년은 사주를 봐야 열리니까. 무엇을 하는 곳인지
모르는 사람에게 잠긴 문 셋을 먼저 보여준 셈이다.

지금은 하나만 묻는다. 대신 이 앱이 **무엇을 하지 않는지**를 먼저 말한다.

> 겁주지 않습니다 — 살(殺)이 붙은 이름도 기운의 결로 읽습니다
> 점수를 매기지 않습니다 — 사람을 숫자 한 개로 줄이지 않습니다
> 생년월일을 가져가지 않습니다 — 계산은 전부 이 브라우저 안에서 끝납니다

이 세 줄이 이 프로젝트의 시작점인데 여태 어느 화면에도 적혀 있지 않았다.

### 오늘의 일진은 장식이 아니다

가운데 낙관처럼 찍히는 글자는 **방금 계산한 오늘의 일진**이다. 눌러보면
다시 찍힌다.

일주는 율리우스일 하나로 정해져서 절기표도 음력 자료도 필요 없다. 그
부분만 `core/day-cycle.ts` 로 떼어놨기 때문에, 첫 화면이 23.6KB 짜리
절기표를 받지 않고도 "이건 실제로 계산한다" 를 보여줄 수 있다.

E2E 는 화면이 말하는 일진을 **율리우스일로 다시 구해서** 맞춰본다.
하드코딩이면 그 검사를 통과할 수 없다.

### 문턱이 되면 안 된다

성공 기준이 "부모님께 링크를 보내드렸을 때 도움 없이 결과 화면까지
도달하신다" 이다. 한 장을 더 두면 탭이 하나 늘어난다. 그래서 두 길을
열어뒀고, 둘 다 테스트로 지킨다.

| | 동작 |
|---|---|
| 공유 링크로 열면 | 인트로를 아예 거치지 않고 결과로 |
| 한 번 본 사람 | 다음부터 메뉴로 바로 |

모바일(320×658)에서 「시작하기」가 스크롤 없이 보이는 위치(y=596)에 있다.

## 화면 구조 — 쌓지 않고 가른다

```
홈  [사주 보기]  [오늘] [궁합] [신년]
      ↓            ↓      ↓      ↓
    입력                별도 화면
      ↓
    인생 타임라인 · 사주팔자        (2.9 화면)
      ├─ [상세 풀이 보기]  용신 · 궁위 · 오행 균형 · 풀이
      └─ [리포트 · 인쇄]   A4 문서 (브라우저 인쇄 → PDF)
```

원안 와이어플로우 그대로다. 한 번 부가 기능을 결과 페이지 하단에 탭으로
쌓아봤는데, 결과 화면이 3.8화면 길이에 버튼 18개가 되면서 대운 타임라인이
주인공 자리를 잃었다.

**문제는 기능 개수가 아니라 쌓아놓은 것이었다.** 홈에서 갈라놓으니
기능을 하나도 잃지 않으면서 타임라인 화면이 깨끗해졌다. 결과 화면의
섹션은 셋뿐이다 — 인생 타임라인(주인공), 사주팔자(근거), 풀이(원국 해석).

부가 화면은 원국이 있어야 열린다. 사주를 먼저 보지 않으면 잠겨 있고,
눌러도 입력 화면으로 보낸다.

상세 풀이도 별도 화면이다. 궁위·오행 균형·풀이를 결과 화면에 쌓았더니
5.2화면이 됐고, 원안대로 갈라놓으니 2.9 + 2.6 으로 나뉘었다.

## 움직임 — 라이브러리 없이

애니메이션을 넣자는 이야기가 나와서 framer-motion 을 **실제로 재봤다.**

```
진입 청크   243KB → 373KB   (+130KB, gzip +42.5KB)
```

관객이 구형 안드로이드 + 느린 회선이다. 애니메이션 하나에 낼 값이 아니라
전부 CSS 로 만들었다.

```
진입 청크   243.07KB → 243.34KB   (+0.27KB)
CSS         20.10KB → 20.92KB     (gzip +0.32KB)
```

결도 다르다. 이 앱은 한지와 먹의 화면이라 튀어오르거나 흔들리지 않는다.
붓이 지나가듯 한 방향으로, 짧게. 최대 이동은 8px 이고 스케일은 안 쓴다.

| 어디 | 무엇 |
|---|---|
| 화면 전환 | 260ms 페이드 + 8px 상승. 입력 → 결과가 이 앱에서 제일 중요한 전환이라 같은 route 안에서도 키를 가른다 |
| 타임라인 칸 | 위에서부터 45ms 간격으로 순차 등장. 여덟 번째부터는 더 늦추지 않는다 — 열 칸을 다 기다리면 애니메이션이 아니라 지연이다 |
| 세로선 | 위에서 아래로 그어진다. 인생이 흐르는 방향 |
| 힘 막대 | 왼쪽에서 차오른다. `scaleX` 라 리플로우가 없다 |
| 칸 펼침 | `grid-template-rows: 0fr → 1fr`. 내용 높이를 몰라도 auto 로 열린다 |
| 계산 중 | 먹이 번졌다 옅어진다. 느린 회선에서 몇 초 걸리는 구간이라 멈춘 게 아니라는 표시가 필요하다 |

### 끝나면 제자리에 있어야 한다

등장 애니메이션은 `opacity: 0` 에서 시작한다. 어떤 이유로 애니메이션이
안 끝나면 **글자가 영영 안 보인다.** 그래서 keyframes 에 `from` 만 두고
`to` 를 비워뒀다 — 끝 상태가 요소 본래의 스타일이라, 애니메이션이 아예
안 돌아도 그냥 보인다. E2E 가 열 칸 전부의 최종 opacity 를 확인한다.

### 움직임을 원하지 않는 사람

관객이 부모님 세대라 `prefers-reduced-motion` 은 취향이 아니라 접근성이다.

원래 있던 규칙은 duration 만 지우고 있었다. **순차 등장을 넣으면서 그게
버그가 됐다** — delay 가 남아 마지막 칸이 315ms 동안 안 보인다. delay 와
반복 횟수까지 같이 지우도록 고쳤고, 그 사실을 테스트로 박아뒀다.

E2E 는 여기서 한 번 더 갈린다. Playwright 는 클릭 전에 애니메이션이 멎기를
기다려서, 등장 애니메이션을 넣자 **28초에서 58초로** 늘었다. 그래서 플로우
테스트는 전부 움직임을 끄고 돈다. 속도만 얻는 게 아니라 **움직임을 줄인
설정에서도 모든 플로우가 되는지가 매 실행마다 확인된다.**

곁가지로 하나 걸렸다. `playwright.config.ts` 의 `use: { reducedMotion }` 이
1.62.1 에서 적용되지 않는다 — 최상위에 넣어도 프로젝트 use 에 넣어도
`matchMedia` 가 false 다. 같은 실행에서 `page.emulateMedia()` 로 직접 걸면
true 가 된다. 안 먹는 설정을 남겨두면 "움직임을 끄고 돈다" 가 거짓말이
되므로 `e2e/fixtures.ts` 에서 page 마다 직접 건다.

## 결과 링크 공유 — 정직한 절충

서버가 없다. 그러니 링크로 결과를 복원하려면 **링크 안에 입력이 들어 있어야
한다.** 이건 암호화가 아니다. 링크를 받은 사람은 생년월일시를 되읽을 수 있고,
되읽을 수 있어야 링크가 작동한다. 그래서 버튼 밑에 그대로 적었다.

> 링크에는 생년월일이 글자로 들어가지 않지만,
> **링크를 가진 사람은 이 사주를 그대로 볼 수 있습니다.**

그럼 왜 `?year=1990&month=5` 로 안 하는가. 막으려는 게 다른 것이기 때문이다 —
**지나가다 읽히는 것**이다. 주소창과 방문 기록, 채팅 미리보기, 오류 리포트.

| 결정 | 이유 |
|---|---|
| 쿼리가 아니라 **프래그먼트(#)** | 서버로 전송되지 않고 Referer 에도 안 실린다. 정적 호스팅 로그에 안 남는다 |
| 비트로 접어 base64url | `#r=E5VxS8AA-Ts` — 11글자. 어깨너머로 안 읽히고, 채팅에서 안 잘린다 |
| 체크섬 **16비트** | 8비트면 손상된 링크가 256분의 1로 통과한다. 통과하면 조용히 *다른 사람 사주*가 나온다 |
| 표준형 검사 | base64 마지막 글자의 잉여 비트만 바뀐 토큰은 체크섬이 못 잡는다. 다시 접어 원본과 대조해 모든 글자가 의미를 갖게 했다 |
| 이름은 안 담는다 | 누구 것인지가 붙는 순간 성질이 달라진다 |

토큰 전 위치 × 전 글자로 한 글자씩 바꿔보는 전수 검사에서 **통과하는 변형이
하나도 없다.** 잘린 링크는 반드시 실패하고, 실패하면 이렇게 말한다 —
"링크가 손상됐습니다. 메신저에서 주소 뒤가 잘렸을 수 있어요."

### 여기서 실제 구멍이 하나 나왔다

원래 설계는 "URL 해시를 아예 쓰지 않는다" 였다. Sentry 가 `location.href` 를
이벤트에 담기 때문이다. 이제 해시를 쓰기로 했으니 세탁이 되는지 확인하는
테스트를 먼저 썼는데 — **브레드크럼에서 실패했다.** `scrubUrl` 은 프래그먼트를
버리지만, navigation 브레드크럼의 `to`/`from` 은 `scrubDeep` 을 거쳐 날짜만
지워지고 있었다. 토큰은 날짜처럼 안 생겼으니 그대로 남았다.

`scrubDeep` 이 URL 처럼 생긴 문자열을 URL 로 세탁하도록 고쳤다.
